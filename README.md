# PatchCore INT8 – Post-Training Quantization for Industrial Anomaly Detection

How much accuracy does [PatchCore](https://arxiv.org/abs/2106.08265) lose when its WideResNet-50
backbone and its memory bank are quantized to INT8 – and how much faster and smaller does it get?

This repository extends the PatchCore implementation of **[anomalib](https://github.com/open-edge-platform/anomalib)**
(Intel, Apache-2.0) with:

* **INT8 static post-training quantization of the backbone** (PyTorch FX graph mode, x86/fbgemm:
  per-channel INT8 weights, per-tensor UINT8 activations, Conv-BN-ReLU fusion, calibration on normal training images);
* **INT8 / FP16 storage of the memory bank** (per-dimension symmetric INT8 scales);
* a **controlled benchmark on MVTec AD** that runs FP32 and INT8 on exactly the same images and reports accuracy,
  latency and size per category;
* a test that verifies the decomposed pipeline is **numerically identical to anomalib's own `PatchcoreModel.forward`**.

The PatchCore algorithm itself (feature pooling, k-center-greedy coreset, nearest-neighbour scoring, anomaly-map
generation) is anomalib's code, used as a library dependency – see `NOTICE`.

## Compared variants

| Variant | Backbone for memory bank | Backbone for queries | Memory-bank storage |
|---|---|---|---|
| `fp32` | FP32 | FP32 | FP32 (anomalib default) |
| `int8` | INT8 | INT8 | FP32 |
| `int8_mixed` | FP32 | INT8 | FP32 |
| `int8_bank_fp16` | INT8 | INT8 | FP16 |
| `int8_bank_int8` | INT8 | INT8 | INT8 + per-dim scale |

`int8_mixed` answers a practical question: can a memory bank built once with the FP32 model be reused when the
deployed model is quantized? Quantization shifts the feature distribution, so this variant isolates that mismatch.

## Method details

**Backbone quantization** (`quantize.py`). `prepare_fx` inserts observers, 32 normal training images (`--calib-images`)
calibrate the activation ranges, `convert_fx` produces a `torch.ao` INT8 graph. The original FP32 module is left
untouched (tested). INT8 kernels run on CPU; the FP32 path may use a GPU for speed, but **all latency numbers are measured
on CPU with batch size 1** so that the comparison is fair.

**Memory-bank quantization.** For a bank `M ∈ R^{N×D}`: `s_d = max_n |M_nd| / 127`, `q = round(M / s)`. Storage drops from
`4ND` to `ND + 4D` bytes. The nearest-neighbour search runs on de-quantized values, so this measures the accuracy cost of
the storage format, not of an integer distance kernel.

**Protocol.** Images resized to 256×256, ImageNet normalisation, layers `layer2`+`layer3`, coreset ratio 0.1,
`num_neighbors=9` (anomalib defaults). Image AUROC from the image anomaly score, pixel AUROC from the anomaly map against the
ground-truth masks over all test pixels. PatchCore has no trained weights, so there is no train/validation tuning that could leak into the test split.

**Scope of the reported run:** 3 of the 15 MVTec AD categories (bottle, carpet, screw), one run on a Google Colab
T4 instance. CPU latencies are from the Colab VM's CPU (2 vCPUs). Run `python -m pcq.benchmark` for all categories.

**Observations from this run**

* INT8 backbone costs 0.7 points of mean image AUROC (98.6 → 97.9 %). bottle and carpet are essentially unchanged; screw drops by 2 points (97.0 → 95.0 %).
* **The memory bank must be rebuilt after quantization.** Re-using a memory bank built with FP32 features for INT8 queries (`int8_mixed`) drops screw to 87.3 % image AUROC: quantization shifts the feature distribution.
* Storing the memory bank in INT8 is free in accuracy (97.8 % vs 97.9 %) and 4× smaller (170 → 42 MB).
* The backbone is 2.1× faster in INT8, but on CPU the **nearest-neighbour search (≈ 1.3 s per image) dominates** end-to-end latency. A deployment would need a faster search (smaller coreset, approximate NN) before backbone quantization matters.
* Three categories and one run: these are indications, not statistically established effects.

## Reproduce

**Without a local GPU:** open `notebooks/run_benchmark.ipynb` on [Kaggle](https://www.kaggle.com/) (free T4 GPU; add the
MVTec AD dataset as input) or Google Colab and choose *Run All*.

**Locally:**

```bash
pip install -e ".[dev]"
python -m pcq.benchmark --root /path/to/mvtec_anomaly_detection            # all 15 categories
python -m pcq.benchmark --root /path/to/mvtec --categories bottle screw    # subset
pytest                                                                     # 12 tests, no data needed
python -m pcq.benchmark --smoke-test                                       # end-to-end check with random weights
```

The smoke test uses a randomly initialised backbone on a tiny generated folder tree. It only proves that the pipeline runs;
its numbers are meaningless and it never writes to this README.

## Limitations

* Only post-training quantization; no quantization-aware fine-tuning (PatchCore's backbone is frozen by design).
* INT8 latency is for PyTorch's x86 CPU backend. GPU INT8 (TensorRT) and edge devices (Jetson, OpenVINO on NPU) are not measured.
* The memory-bank INT8 path stores INT8 but searches in float; an integer distance kernel is not implemented.
* MVTec AD only; it is a well-studied benchmark and does not represent every production setting.
